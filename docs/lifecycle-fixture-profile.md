# Health M1 synthetic lifecycle fixture profile

This profile is a local-only adapter for three deterministic logic cases from the pinned Health workflow sources: receiver duplicate-batch, receiver mismatched-state, and lifecycle create when the list is empty. The source files remain the inputs; the exported definitions are separate generated artifacts with separate hashes. The adapter refuses source drift, an unknown case/action type, duplicate JSON properties (case-insensitive), unknown profile fields, and reuse of an output directory.

The generated receiver replaces its Graph and Teams actions with fixed Compose values. The lifecycle workflow uses a manual request trigger and sends its two exercised HTTP operations (`List_subscriptions` and `Create_subscription`) only to a secure `FixtureStubCallback` parameter. A generated response-stub definition returns deterministic fixture envelopes. The exported configuration contains no callback URL or credential. If deployed, the lifecycle fixture requires network access to that supplied response stub; only the export/test tooling itself is local and provider-free. This tests intended local logic only; it does not validate Health, Graph, Teams, managed identity, Azure deployment, or live workflow behavior.

The bound profile has three outer trigger invocations and two nested stub trigger invocations, with retry policies disabled on each transformed HTTP action. Its inclusive trigger total is five against a proposal limit of twenty. Conservative potential action activations total 32 (14 + 9 + 9, including both nested response-stub actions) against a limit of 40. Aggregate input plus nested request/response fixture payload is capped at 10 MiB; logs are capped at 100 MiB. These are planning and offline-ledger bounds, not Azure billing measurements or runtime enforcement. The billing estimate treats each potential Logic Apps action activation as one conservative action unit; actual billing may differ.

The offline activity ledger counts outer and nested invocations, configured retry attempts, action activations, payload bytes, and log bytes. It rejects duplicate event identifiers, out-of-order retries, and any event that crosses a bound rather than hiding activity. The generated artifact manifest records the source/profile/generated-file/configuration hashes independently. Each output file is opened with `CreateNew`, and output ancestry is rechecked for reparse points before writes. This prevents overwriting an existing file and fails closed on observed path collisions. It does not provide an OS-level reservation against a same-user process racing directory creation; partial output is preserved on any collision or failure.

Lifecycle evidence keeps the operation result separate from resource absence. A successful delete plus zero process exit and observed absence is the only pass. An unknown/lost delete result, nonzero teardown, or no-op cleanup remains incomplete even if absence is observed. Absence is a recovery observation; it cannot establish which actor created a resource or prove restoration of shared resources. The profile grants no cleanup authority and creates no Azure resources.

The generic lifecycle evaluator and its seven stages are a separate component. These case records belong under `intended-function`; they must not be relabeled as target, deployment, payload-readback, or teardown evidence. The adapter profile is separately pinned to source commit `4d3273335aed8f59dc4df2151f28e8694dced7d9` and the LF-normalized SHA-256 hashes of the two original workflow files. M1 does not promote legacy harness exit codes into lifecycle qualification. Live trigger/action/log enforcement remains an M2 requirement.
