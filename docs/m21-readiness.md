## Resource group deletion monitors

Cleanup prefers `Azure-AsyncOperation` when that header is present and uses
`Location` only when it is absent. An invalid preferred header refuses; it does
not fall back to another header. The initiating DELETE version is not assumed
to be the monitor version. The source policy accepts the independently returned
stable versions 2018-08-01, 2020-10-01, 2021-04-01 and 2022-09-01, with only the
optional `monitor=true` query parameter. New versions or query parameters need
source-policy review rather than an arbitrary URL allowance.

Monitors remain HTTPS on management.azure.com, in the selected subscription,
under subscription operationresults or Microsoft.Resources westus2 operation
results/status paths. Credentials, fragments, encoded selectors, duplicate or
unrecognized query keys, foreign hosts/subscriptions/providers and resource
write routes refuse. The full validated URL, selected protocol and bounded
Retry-After are journaled before polling. Workers require that exact recorded
URL, including its query, and a fresh durable poll slot before authentication.
Unvalidated URLs or capability query values are never logged.

Async-status monitors require an explicit Succeeded status. Location monitors
distinguish HTTP202 pending from HTTP200/empty204 completion; contradictory,
malformed, Failed or Canceled responses cannot qualify. Bounded Retry-After
delays must fit the original recovery deadline. The twelve monitor poll slots
are shared across restarts; consumed or interrupted slots are not refunded.
If a poll has no durably saved status/Retry-After, recovery waits the maximum
accepted sixty-second delay before a further GET, or refuses if it cannot fit
the original deadline. Missing timing never permits immediate polling.
Recovery reuses recorded success, permanently refuses recorded failure, and
never sends another DELETE. Exact group and all four workflow absence checks
are still required after monitor completion. Monitor provenance is restored
before those ordinary resource reads.

`verifiedDisposal` requires acknowledged deletion, a proven monitor completion
(or a durably recorded synchronous200/204 without monitor headers), and typed
exact-target absence. HTTP202 without a monitor, missing/invalid monitor
provenance, legacy path-only records and unknown DELETE outcomes can yield
observed absence but cannot become verified disposal. Historical receipts are
not rewritten or upgraded by this source change. Existing pinned proposals and
approvals must be rebuilt/reviewed for any future live use of changed source;
offline tests provide no execution or deletion authority.

The synthetic `test_m21_delete_monitor.py` suite exercises header precedence,
monitor API/query preservation, restart recovery, shared poll limits, terminal
failure, unknown outcomes and worker rejection of query substitution through
the framed fake transport. No Azure, token acquisition or live DELETE is used.
